## (5) Genome as a SPARSE packing mechanism — revisited, staying sparse
The srmech genome IS bounded sparse packing (the anti-dense guard is structural):
- `genome(kernels=[(label, leaves)…])` packs many kernels into ONE telomere-partitioned strand; `encode_shape(n)` partitions a kernel of size n into **≤256-leaf "tomes"** (`leaf_cap=256`), recursing into **`quad_strand`** (depth grows) past that — it **never** makes a dense n-vector. Caps **`LEAF_CAP=256` / `MOBIUS_CAP=1024` / `QUAD=4`** are enforced (`GenomeBoundingError`). `genome_catalog` returns an attested manifest (`leaf_dim` / `n_turns` / `body_sha256` / per-chromosome `cap_sha256` / `leaf_count`); `genes(strand)` recovers `[(label, leaves)…]` — **Siona introspects via `genes`/`genome_catalog`**.
- **Why it went dense last time (and the fix):** the dense blowup = materializing **dense HDC vectors** into the genome leaves (leaf_dim × n_leaves). **STAY SPARSE: a leaf stores the turn-RECIPE** (the bounded shape-encoding of the token-recipe + `k*` + sub-language tags + address index) — **never the vector.** Siona **regenerates** the Klein-4 HDC deterministically (`byte_k4` seed + the de Bruijn walk) at recall time. The caps make a dense blowup *impossible* by construction (a leaf is bounded to ≤256; bigger kernels recurse into bounded leaves).
- **The Siona genome (PKG-3):** one bounded, attested, introspectable `.chr`/packed genome replacing the loose 384 MB NDJSON + index — genes = article-recipes + the kernel TOMLs (already sparse). Ships **with** siona (smallwiki genome as package data; bigwiki as a downloadable if the recipe-genome fits disk).

## CORRECTION (2026-06-21) — "kernel" is triple-meaning; NONE is a stored HDC instrument (user caught the conflation)
F897 above sloppily grouped `formatting_language_kernel.toml` with "the instrument." They are different layers. The word **kernel** names THREE distinct things, and **none is a persisted RBS-HDC vector blob** (verified: every corpora file — `_sparse_kernel.json` / `_assoc.json` / `_cooc_tomes.json` / `_fullbody_index.json` / `instrument.ndjson` — has **0 dense float-vectors**):

1. **Comprehension/parse kernels** — `formatting_language_kernel.toml`, `bit_exact_comm_kernel_descriptor.toml`, `asl_sign_kernel.toml`. **CONFIG**: cascade recipes for HOW to parse/route markup & sub-languages (the form-layer + the `[router]`). This is the **pre-processor** layer — "config/navigation information FOR kernels," exactly as the user read it. NOT the instrument.
2. **Knowledge recipe** — `simplewiki_fullbody_instrument.ndjson` (`t/k/n/u/s`): the **token bytes** that regenerate the HDC.
3. **Association kernels** — `simplewiki_full_sparse_kernel.json` (`vocab`+`edges`+`freq`), `simplewiki_assoc.json` (`assoc`): sparse **Class-L co-occurrence GRAPHS** (adjacency), not vectors.

**The actual RBS-HDC instrument** (the Klein-4 vectors, the chunked-M pages, the bound key→token relationships) is a **RUNTIME object** — regenerated deterministically (`byte_k4` → Klein-4 → `chunk_bundle`) from the recipe at recall, and **never persisted as vectors** (F879/F893/F896 build it in memory and discard it). **There is NO "RBS-HDC kernel" file — by design** (a persisted vector blob IS the dense thing we refuse). The instrument's persisted form = the **sparse recipe** (the NDJSON now; the bounded genome later, §5 above); its HDC form is computed on demand. So §5's genome packs **recipes**, regenerates HDC — and the genome is NOT, and must never become, a vector store. The "loose kernels" of §4 are: the **parse-config** TOMLs + the **recipe** NDJSON + the **graph** JSONs — three sparse layers, no HDC vectors among them.
