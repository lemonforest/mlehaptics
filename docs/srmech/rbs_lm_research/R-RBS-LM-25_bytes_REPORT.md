## §0 Human walkthrough

**What we're doing.** Every RBS-LM instrument up through R-RBS-LM-24 inherited BPE tokenization from GPT-2 — 50,257 tokens, English-distribution-biased merges, dependency on `transformers` library at inference time. The user identified this as a *privilege* baked into the substrate: BPE's merge frequencies encode the English-heavy training corpus structurally, and any model built on BPE tokens carries that bias even if its WEIGHTS were retrained for another language. This partition removes BPE entirely.

The replacement is **byte-level**: each UTF-8 byte (0..255) is a token, minted via Class A content-addressing (`f"LoE.byte.{n}"`). Vocab size drops from 50,257 to 256 — 196× smaller. Tokenization becomes `text.encode('utf-8')` — Python stdlib, zero external dependency, language-agnostic. The same byte sequence encodes English, Chinese, Arabic, code, and emoji equally.

Two variants:

1. **Variant A (GPU-less from text)** — same harvest path as R-RBS-LM-24 GPU-less but at byte resolution. Tokenize the research notebook as UTF-8, slide a context window, encode (byte_context, next_byte) pairs from the actual notebook text. No teacher model anywhere.

2. **Variant B (Path D: distill BPE source to bytes)** — this is the substantial one for your hope. Use GPT-2 to GENERATE text (so its trained content shows up); retokenize the generated text as UTF-8 bytes; encode (byte_context, next_byte) pairs from THAT byte stream. The resulting instrument has byte-level vocab + byte-level inference: zero GPT-2 dependency at serve time. **The BPE tokenization is structurally stripped — the English privilege is removed.**

**Why this matters (your framing carries cleanly).** Per your 2026-05-25 stance: *"the 3.3% ceiling is likely structural — driven by the rotation that wet nets do."* You explicitly anticipated that byte-level wouldn't lift the ceiling — what you wanted to find out was whether the SURFACE (language-agnostic; BPE-stripped) was operationally achievable. That's the test the partition runs.

**Honest result (the framework reading per the falsification discipline).** The byte-level surface works. The byte-level OUTPUT QUALITY at our 600-observation scale is **worse** than BPE Path C — both variants mode-collapse to single-byte repetition (`'                    '`, `'tttttt'`, `'eeeeee'`, `'\x10\x10'`). The reason is exactly what R-RBS-LM-17 §3.2 identified: BPE+WTE Path C gave us SEMANTIC CLUSTERING for free (` the` vs ` The` cosine ≈ 0.49) — that was the load-bearing structure for the 3.3% lift over zero. Pure srmech-native Class A byte mints have no clustering signal at this scale; the cleanup converges to the most-frequent-byte fixed point. **This confirms the 3.3% wasn't just a number — it was the WTE-induced clustering specifically.**

**How srmech automates it (future state per R-RBS-LM-12 §6).** When srmech-fix lands the v0.5.0rc, both variants absorb into `srmech.rbs_lm.bytes` with a server flag:

```bash
srmech rbs-lm serve --byte-mode --instrument path-d-distilled.bin --port 8788
```

Clients point any OpenAI-API tool at `http://localhost:8788/v1` and talk to a language-agnostic local expert. The wire surface is unchanged from R-RBS-LM-24; the substrate is. **The "unquantized LLM at edge" framing now has a language-agnostic variant.**

## §3 Implementation

### §3.1 `rbs_lm_bytes.py` — byte-level encoder + vocab

```python
BYTE_VOCAB_SIZE = 256

def byte_vec(n, D=8192) -> bytes:           # Class A mint: f"LoE.byte.{n}"
def compute_byte_vocab_table(D) -> ndarray  # shape (256, D//8); 256 KB
def encode_context_bytes(byte_ids, vocab_table, D)  # Kanerva sequence; byte vocab
def encode_observation_bytes(ctx, nxt, vocab_table, D)  # bind(ctx, byte_vocab[nxt])
def vectorised_cleanup_bytes(cand, vocab_table, D, top_k)  # 256-row argmin Hamming
def text_to_bytes(text) -> list[int]    # text.encode('utf-8'); language-agnostic
def bytes_to_text(byte_ids) -> str       # bytes(...).decode('utf-8', errors='replace')
```

Same structural shape as R-RBS-LM-17 Path C — just byte vocab instead of WTE projection.

### §3.2 Two encode scripts

| Script | Source signal | Source-model fetch needed? |
|---|---|---|
| `encode_bytes_variant_a.py` | Actual next byte in notebook text | **No** — pure substrate-native |
| `encode_bytes_variant_b.py` | Next byte in GPT-2-GENERATED text | Yes for generation; **not** for inference |

Variant B's structural contribution: the source model is used ONLY to produce a corpus; its tokenization is stripped via UTF-8 retokenization. The resulting instrument has zero BPE dependency at inference time.

### §3.3 `RBSChatbotBytes` (in `rbs_lm_chatbot.py`)

Sibling of `RBSChatbot`. Same protocol (`load` / `respond` / `respond_with_metadata` / `converse` / `_generate`). Differences:
- `load`: no `transformers` import; no source-model fetch; vocab table built from Class A mints
- `respond`: `prompt.encode('utf-8')` instead of `tokenizer.encode(prompt)`
- `respond` default `max_new_tokens=80` (byte-level needs ~5× more steps than BPE for comparable English output)
- decode uses `bytes_to_text` with `errors='replace'` for partial multi-byte safety

### §3.4 Server `RBS_LM_BYTE_MODE=1` routing

```python
if BYTE_MODE:
    _bot = RBSChatbotBytes.load(instrument_path=INSTRUMENT_PATH)
else:
    _bot = RBSChatbot.load(instrument_path=INSTRUMENT_PATH, use_path_c=True)
```

`/health` declares `byte_mode: true` and `tokenization: "utf-8 bytes (V=256; no BPE)"`. The framework_reading text appends a sentence about BPE-stripping in byte mode. OpenAI-API client surface is unchanged either way — the same endpoints, same wire format.

### §3.5 What the partition does NOT do

- **Lift the 3.3% ceiling.** Anticipated; confirmed. The ceiling is structural per the discrete-cascade-can't-replicate-attention-rotation argument (R-RBS-LM-19 falsification).
- **Avoid mode collapse.** At our 600-observation scale, the byte-level cascade lacks the WTE-induced semantic clustering that BPE Path C exploited. Mode collapse to most-frequent-byte fixed points is the observed behavior. Larger-scale encoding (millions of byte observations) might lift this; not tested here.
- **Multi-byte UTF-8 character coherence at the byte cascade level.** The cascade picks bytes; if it outputs a partial multi-byte sequence, `errors='replace'` renders U+FFFD. The cascade doesn't know about codepoint boundaries.
- **Streaming.** Same 501 as R-RBS-LM-24 server; not implemented.
- **Byte-level Path C analog (byte-embedding via some other source).** No source-model byte-embedding exists; could synthesize byte n-gram features if a later partition wants to try.

## §5 Framework-reading findings

**Finding 1 — Byte-level surface is language-agnostic and operational.** Per §4.4 + §4.5. 8/8 multi-language prompts accepted across both variants; OpenAI-API end-to-end works in byte mode; tokenization is `text.encode('utf-8')` (Python stdlib only). The English privilege from BPE is structurally absent.

**Finding 2 — Path D distillation procedurally works.** Per §4.3. GPT-2 was loaded, used to generate 10,402 bytes of corpus, then dropped. The resulting instrument carries GPT-2's content WITHOUT its tokenization. The procedure generalizes to any BPE-trained source: load → generate → retokenize as bytes → encode (byte_context, next_byte) → save → drop source. **Your hope — "make every existing BPE model become byte level" — is procedurally validated.**

**Finding 3 — The 3.3% ceiling IS structural, AND byte-level falls BELOW it.** Per §4.4. Both byte-level variants mode-collapse to single-byte repetition. R-RBS-LM-17 §3.2 had attributed the 3.3% lift over zero to WTE-induced semantic clustering — pure srmech-native Class A byte mints have no clustering signal at the 600-observation scale we tested. The cleanup converges to the most-frequent-byte fixed point. **This confirms two things at once:** (a) your structural-ceiling read is correct (byte-level doesn't lift it); (b) the WTE clustering was load-bearing for staying ABOVE the noise floor (without it, we drop to Path-B-territory mode collapse).

**Finding 4 — Mode-collapse pattern differs across variants — both lose, but predictably.** Per §4.4. Variant A (GPU-less notebook) collapses to ASCII space (most-frequent byte in English prose). Variant B (Path D from GPT-2) collapses to different fixed points per-prompt — `t`, `e`, `d`, `\x10` — reflecting the byte-frequencies in GPT-2's generated text being slightly different from notebook prose. Neither produces coherent multi-byte sequences.

**Finding 5 — Per-byte latency is FASTER than per-BPE-token latency.** Per §4.4. Byte-level: ~60 ms/byte (V=256 cleanup). BPE Path C: ~180 ms/token (V=50,257 cleanup). 3× faster per step. But 5× more steps for comparable English output (BPE compresses average ~4.5 bytes/token). **Net latency for an English response is ~5× × ~3×-faster = ~1.7× slower.** For non-ASCII (Chinese ~3 bytes/char, emoji ~4 bytes/char), the multiplier varies. Net: byte-level is operationally slower for English, comparable for short multi-byte content.

**Finding 6 — D/N capacity formula validated.** Per §2 + R-RBS-LM-21. V=256 gives ln V ≈ 5.5; D=8192/N=621 gives D/N ≈ 13.2 >> 5.5 (well above floor). **The capacity formula was not the bottleneck.** What WAS the bottleneck: vocab clustering structure. Capacity vs structure are orthogonal failure modes.

**Finding 7 — The §0 human-walkthrough discipline continues to scale.** Per §0. R-RBS-LM-22 single-deliverable / R-RBS-LM-23 three-deliverable / R-RBS-LM-24 five-deliverable / R-RBS-LM-25 two-variant-with-honest-negative-result — all applied §0 cleanly. The pattern accommodates positive AND negative findings without losing coherence.

**Finding 8 — The substrate-native discipline does NOT magically improve output quality.** Per §4.4. Class A content-mint of byte values is the maximum-substrate-native vocab — and it produces worse output than the cross-substrate WTE projection. **This is an important framework reading:** substrate-nativity is a *structural* property (provenance, no privilege, no external dependency), not a quality-of-output property. The user's "no privileged primitive classes" stance applies to the substrate definition; output quality is a separate dimension.

## §7 Open threads (not blockers for partition close)

- **Larger-scale byte-level encode.** At 600 obs we mode-collapse. At 50,000 obs (full notebook; multi-threaded R-RBS-LM-11 path) the byte-byte transition statistics might be rich enough to support varied output. Not tested.
- **Byte-embedding via n-gram features.** Class A content-mint of `f"LoE.byte.{n}"` has no clustering structure. Alternative: mint `f"LoE.bigram.{a}.{b}"` for n-grams as a clustering scaffold — would land between pure byte-level and full BPE. Not explored.
- **Per-language byte-frequency profiling.** Variant A collapsed to space; Variant B to varied fixed points. Suggests byte-level cascades reflect their corpus's byte-frequency distribution very directly. Could inform corpus design for specific-language byte-level experts.
- **Tokenizer fallback for clients expecting `tiktoken`.** Some clients use `tiktoken.encoding_for_model(model_id)` for client-side token counting. For unknown model_ids (`rbs-lm-v25b-byte-distilled-gpt2`), they typically skip token counting. We could publish a `tiktoken`-shape "byte" encoding for the rare client that requires one. Deferred.
- **Path D from non-English source models.** We tested with GPT-2 (English-heavy training). The same procedure with a Chinese-trained BPE model (e.g., Qwen base) would distill that model to language-agnostic byte-level — letting different-language-trained models contribute content to one byte-level local expert. Sister-direction worth exploring.
