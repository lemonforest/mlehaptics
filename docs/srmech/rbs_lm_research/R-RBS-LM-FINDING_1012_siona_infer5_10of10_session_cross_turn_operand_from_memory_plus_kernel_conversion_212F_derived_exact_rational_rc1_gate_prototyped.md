## The reading (what the two challenges prove)
- **Challenge 1 — the utterance is not the only operand source.** "the boiling point of water" supplies no digit; the drive loop detects the operand deficit (all signature-fits 0), sim-recalls the referenced note from working memory (query = utterance minus numbers/operators/tool-name → "boiling point water" → the water note), extracts 100, and completes `gcd(100,48)=4`. Working memory is now a first-class **operand namespace** — a turn can refer to what a previous turn established, which is what makes it a *session* rather than a sequence of one-shots.
- **Challenge 2 — answering ≠ retrieving: the kernel composes.** 212 exists nowhere in memory. The answer machinery: (i) the asked unit (`fahrenheit`, the token after the interrogative operator) selects the **ingested kernel** — itself just a remembered note parsed as a declared linear-map form (`<target> is <source> times a over b plus c` — operator words `times/over/plus` are declared; the coefficients are content); (ii) the kernel's *source* unit (`celsius`) selects the **fact** (sim-recall, kernel-notes excluded; value = the integer immediately before the unit token); (iii) the composition runs **exact-rational**: `(v·a + c·b)/b = (100·9+32·5)/5 = 1060/5`, reduced by srmech `cyclic.gcd` (Class I) to `212/1`, collapsed to "212" only at display. **This is the RBS thesis in one turn:** the kernel IS a stored relationship (fahrenheit↔celsius as integer coefficients), and inference = composing stored relationships — no float, no lookup table, no hardcoded conversion.
