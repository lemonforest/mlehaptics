## The reframe (the user's, sharpened)
"Be detailed" was implemented as a **static cap on ONE axis** — sentence count (gloss = 1, abstract = ≤3). That's wrong twice over:
1. **It's not NOW-dynamic.** Detail is relative to *what was already given in this conversation*. If I served 3 sentences and the user still reads it as brief, "more detail" must **escalate** — not re-serve the same fixed chunk. The NOW (the running context) must dictate the level.
2. **It's not linear.** "More detail" is **not** "move this one viewport toward a destination" (more sentences of the same article). The viewport's **perspective has degrees of freedom we forgot**. Detail = **open another DOF**, a different *facet* of the same thing — not more of one axis.

**The forgotten DOF are already built** — they're the tiers we made separately: the **abstract** (text axis), the **relations** (relational axis: what X does/connects to), the **associations** (what X appears with), and the **spectral neighbourhood + web** (community axis: X's tome, its parent clump, its cross-domain bridges — F791/F792). "Be detailed" should **open these DOF**, NOW-selected — which unifies *detail* and *navigation*: deepening IS riding the clumps-of-clumps.

## First step (implemented)
On **depth=long** ("tell me more / in detail / be detailed", F763), the definition/abstract tier now opens the **spectral-neighbourhood DOF** on top of the abstract + relations + assoc:
- `tell me more about tomato in detail` → the ≤3-sentence abstract **+** `(related: →sauce, →soup, →ketchup…; ketchup, fruit, vegetable, pizza, mozzarella…)` **+** `(deeper — another facet, its spectral neighbourhood: cuisine, salad, sauces, onions, lettuce; bridges to food~cuisine)`.
So detail = **abstract (text) + relations (relational) + neighbourhood/web (community)** — multiple DOF of the one viewport, not more sentences on the text axis. The static-cap feeling is gone; the "deeper" line is the F792 navigation opened as a *facet of detail*.

## The NOW-dynamic part (the follow-on, designed not built)
The cross-turn escalation the user describes — *"I thought I was detailed, the user sees it as brief, so NOW be-detailed = an etak journey"* — needs **conversation state**: track which DOF have been opened, and on a *repeat* push ("still too brief / more / go deeper") **open the next DOF** (abstract → +relations → +neighbourhood → +web-hop → +sibling sub-clumps → … → article body when stored). The depth signal becomes a **level that advances with the NOW**, not a binary. (Today's depth is binary short/normal/long; the escalation ladder + per-conversation level is the next build; F759's running-context object is where the level lives.)

## Honest scope
- First step opens ONE extra DOF (the neighbourhood) on long; the full ladder (escalating DOF on repeated pushes, NOW-tracked) is designed, not built — it needs the per-conversation detail-level state.
- The article BODY (more text on the linear axis) is still not stored (the §3 data limit) — so the *text* axis maxes at the lead paragraph; the **other DOF** (relational/community) are where deepening now goes (which is the point: detail isn't only-more-text).
- srmech-native (the neighbourhood facet rides the F791/F792 tome-tree); no abs/CAD.

## Verdict
The 3-sentence cap was the wrong *shape* for "be detailed": detail is **not a static cap on the sentence axis** — it is **NOW-dynamic** (relative to what was already given) and **multi-DOF** (the viewport's forgotten degrees of freedom = the relational / community / web facets we built as the navigation, F791/F792). First step shipped: depth=long opens the **spectral-neighbourhood facet** alongside the abstract + relations, so deepening = opening another DOF, not more sentences on one axis — *detail and navigation unify*. The NOW-dynamic escalation ladder (each "still too brief" opens the next DOF, tracked in conversation state) is the designed follow-on.
