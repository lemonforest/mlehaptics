## The reading (the loop, and what signature-fit buys)
- **The full drive loop runs on the sparse substrate + srmech's own typed schema.** (a) INFER-2 grounds the utterance to top-K tool candidates; (b) operands are extracted from the utterance (ints via regex, bytes via the "bytes/of X" tail); (c) **signature-fit** scores each candidate by how the operand *shape* matches the tool's *typed parameter* shape; (d) the dotted name resolves to the callable (importlib walk); (e) args bind positionally by type; (f) the real op **runs**; (g) the result is read back into never-compacted working memory. No hand-rolled dispatch — it drives srmech's *declared* tool_schema.
- **Signature-fit is the disambiguator INFER-2 needed (F1008's flagged lever).** `factor 360` grounds to `factor` top-1, but a naive "prefer more params" re-rank jumped to `crt_combine` (2 list-params) and jammed `[360]` into it → runtime error. **Exact-arity fit** — reward the tool whose required scalar params exactly consume the operands, treat list-params as a *weak* fit when the user gave scalars — correctly selects `factor` (1 int-param ← 1 int operand). This is F769's "usage overrides the definition-bag" made operational for tools: the *operand shape* (usage) overrides the *grounding-sim* (definition) when they disagree.
- **INFER-2 + INFER-3 together = the core of the rc1 gate.** Natural utterance → grounded tool → operand-fit → real op run → result in memory. That is "native infer to drive srmech." The two hardest technical milestones of the five-gate roadmap are now prototyped; INFER-1 (intent router) and INFER-4 (self-CLI) *reuse* these two, and INFER-5 is the multi-turn wrapper around this exact loop.

## Honest scope
5/5 is a clean demonstration on int/bytes/list-typed scalar ops with clear operands — the milestone's DoD ("emit + run ≥1 real srmech op end-to-end") is met with margin. It is a first build, not rc1-ship-ready: operand extraction is heuristic (regex ints + a bytes-tail rule — no floats, matrices, HV operands, or named/keyword args yet); type coverage is int/bytes/list (the 300+ tools taking `Mat`/`Vec`/`HV`/`Poly` operands need structured-operand parsing); there is no error-recovery loop yet (a failed run should re-rank to the next candidate — trivial to add, the working-memory ERR capture already surfaces it). The eval utterances are a hand-authored harness (test inputs, not stored content). Sparse Klein-4 grounding throughout; the run is genuine srmech. No fluency claim — this is tool-driving, not generation.
