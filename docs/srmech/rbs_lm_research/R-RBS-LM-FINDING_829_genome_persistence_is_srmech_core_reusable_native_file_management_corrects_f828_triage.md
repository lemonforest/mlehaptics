# F829 — CORRECTION to F828: genome persistence / native file-management is srmech-CORE, not siona-layer-to-close. It is a REUSABLE primitive so that ANY package building on srmech ships one native genome file instead of loose kernels — "we use it our way" (user direction). srmech already SHIPS it (`srmech.amsc.genome`: `genome_save/load/append/remove/replace/pack/window/catalog/export/import` + `encode_shape` + `recall`, over native `genome_*_c`), AND siona's genome script ALREADY uses it (`g.genome_save` / `g.genome_catalog`) for its kernel bookshelf. But it lives in the 0.7.5rc series only (production 0.7.4 has NO `srmech.amsc.genome`), so it GRADUATES with srmech v0.7.5 — making 0.7.5 the linchpin for both the native-genome siona recall AND the EC-recall.

**Date:** 2026-06-17 · **srmech:** 0.7.5rc173 (has `srmech.amsc.genome`); production 0.7.4 does NOT · **Provenance:** `srmech.amsc.genome` surface probe (rc173 vs 0.7.4) + siona genome-script usage audit (`g.genome_save` line 398, `g.genome_catalog` line 535) · **Composes / corrects:** F828 (the triage this fixes), [[project_siona_package_takeover_unmirror]], PKG-1/PKG-2 (#229/#230), UPSTREAM §41/§43/§44/§45/§49 · **User direction (2026-06-17):** "scaffolding for genome persistence can be srmech core items that we use our way is the goal. so that any other packages that build off srmech can package native file management instead of loose kernels."

## The correction
F828 classified the genome asks (§41 persistence, §43 file-management, §44 biology-faithful, §45 editing) as "siona-layer — close on srmech's side." **That was wrong.** The user's principle: native file-management is a REUSABLE srmech-core primitive. The CAPABILITY (save/load/append/edit/window/catalog a native packaged genome) belongs in srmech so every downstream package (siona, ephemerides-spectral, chess-spectral, …) ships ONE native genome file instead of loose JSON/kernel files; only the SPECIFIC layout/usage is the downstream package's. So §41/§43/§44/§45 STAY srmech-core — and they are largely DONE.

## Verified state
- **srmech-core (the reusable native file-management) is BUILT:** `srmech.amsc.genome` exposes `genome_save(strand, path, the_one, labels)`, `genome_load`, `genome_append(path,label,leaves,the_one)`, `genome_remove`, `genome_replace`, `genome_pack`, `genome_window` (page in ONE chromosome), `genome_catalog`, `genome_export`/`import`/`explode`, plus `encode_shape(n)` (the encode criterion) and `recall(strand, the_one, telomere)` — over native `genome_*_c` symbols. It is the DNA-bookshelf model (F711/F713/F715, UPSTREAM §41/§44).
- **siona ALREADY uses it** for its kernel bookshelf: the genome script calls `g.genome_save(strand, path, ONE, labels)` + `g.genome_catalog(...)`. So the "package native file-management, not loose kernels" principle is already realized for siona's KERNELS.
- **The one remaining loose store** is siona's FULL-BODY recall instrument (`simplewiki_rawbody_instrument.ndjson`, ~400 MB, + the JSON offset index). Making THAT a native srmech genome (one chromosome per body, `genome_window` to page a body, `recall` to walk it) is the concrete realization of the directive (PKG-3).
- **It graduates with 0.7.5:** production srmech 0.7.4 has NO `srmech.amsc.genome` (ImportError) — the genome surface is in the 0.7.5rc series only. So any siona feature that USES the native genome (the native-genome recall) gates on srmech v0.7.5 reaching production — same gate as the EC-recall (rc171-native triality).

## Re-mapped 0.7.5 graduation gate (corrects F828's triage)
The reusable core siona (+ downstream) needs is **already built in the 0.7.5rc series**: native genome file-management (§41/43/44/45), native klein4 (§53), native triality cycle (F826), `klein4_unbundle` (§54). So graduating 0.7.5 is mostly **verify + cut the clean tag**, not a big build. The still-open asks (§39 class-generator, §50 streaming bundle-accumulate, §51 sparse Fiedler #1097, §52 low-RAM encode) are reusable-core *enhancements* — the user's call whether they block 0.7.5 or defer to 0.8. None of them block siona's needs (genome + klein4 + triality + unbundle are in). I do NOT close any upstream ask ([[feedback_create_upstream_issues_never_close_them]]) — this is the map.

## Consequences (queued)
- **PKG-3:** package siona's full-body instrument as a native srmech genome (genome_save/append/window/recall) — ship native file-management, not the loose NDJSON+index. Gated on srmech v0.7.5 to production (for the siona PACKAGE; the live server on rc170 can prototype now since the rc series has the surface).
- The siona PACKAGE dep floor rises to `srmech>=0.7.5` the moment its recall uses the native genome (or native triality) — reinforcing 0.7.5 as the linchpin (F828).

## Verdict
Genome persistence/file-management is srmech-CORE (reusable native file-management so downstream packages ship native, not loose kernels) — correcting F828. It is built in the 0.7.5rc series and siona already uses it for kernels; the full-body instrument is the remaining loose store (PKG-3). Production 0.7.4 lacks it, so it graduates with srmech v0.7.5 — the linchpin for native-genome siona AND the EC-recall. The 0.7.5 gate is now mostly verify-and-cut plus an optional enhancement triage (§39/50/51/52), the user's call.
