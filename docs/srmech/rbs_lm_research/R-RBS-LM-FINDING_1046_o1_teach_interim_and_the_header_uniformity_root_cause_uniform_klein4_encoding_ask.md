# F1046 (user design-critique: is the back-compat route right, or should the genome encoding be uniform?) — **the O(1) incremental-teach path works as an INTERIM (`genome_store.add_kernel`: chunk the D=8192 kernel to 32 leaves, header-less `genome_append`, `kernel_unpack` back-compat recovers D=n_leaves×leaf_dim exactly — O(1), ~12 ms flat, prior kernels untouched), BUT it exposes a real ROOT non-uniformity the user named: the §60 kernel HEADER is a byte-TLV block (marker 0x4B) embedded in a Klein-4 leaf stream — the SOLE non-Klein-4 residue in a store whose content codec is `klein4`-identity (F1043). That is WHY append can't be uniform (the header can't ride `genome_append`, which takes raw Klein-4 leaves) and WHY a mixed genome appears (static chromosomes header'd, taught ones header-less). The fix is not a kernel-aware append (treats the symptom) but making the encoding UNIFORM: (A) Klein-4-encode the header into a leaf (base-4 the D/element_type/leaf_dim; portable, in-memory strands self-describe) or (B) move D to the manifest and drop the in-strand header (simplest; directory-only). Either makes the store uniformly Klein-4 AND the O(1) `genome_append_kernel` a consequence. Filed #1261 / UPSTREAM §89. `add_kernel` ships as the honestly-labeled aligned-D interim until the uniform format lands.**

## Grounded (rc123)
```
INTERIM (add_kernel): chunk D=8192 -> 32 leaves (8192 = 32×256, aligned); genome_append (O(1), ~12 ms flat);
  kernel_unpack back-compat trim (D = n_leaves × leaf_dim) recovers EXACT. Prior kernels byte-untouched.
  GUARD: D not a multiple of leaf_dim raises -> needs the header (no public O(1) kernel-append; #1261).
ROOT CAUSE (user): the §60 header (0x4B) is a byte-TLV block in a Klein-4 leaf stream -> NOT Klein-4 ->
  can't ride genome_append -> the mixed-genome smell. It is the one non-identity residue (content is klein4-identity).
FIX (uniform): (A) base-4-encode the header INTO a Klein-4 leaf, or (B) put D in the manifest, drop the header.
  Both -> uniformly Klein-4 + O(1) append; the kernel-append we wanted is a consequence, not a feature.
```

## The reading
- **Why this route:** the append friction was a FORMAT collision, not an append limitation — the header isn't Klein-4, so it can't ride the raw-leaf `genome_append`. I chose O(1) header-less append over an O(N) rebuild, accepting a mixed genome. The user's read is sharper: the mixed genome is a *symptom*; the byte-TLV-header-in-a-Klein-4-store is the *cause*.
- **The translation goes INTO Klein-4, not out of it.** "Uniform across chromos" = translate the *header* into Klein-4 (base-4 the metadata), keeping the *content* element_type recorded in that header — uniform container, variable content. That is the honest generalisation of the F1043 identity-codec: today the content is klein4-identity and only the header breaks it; encode the header too and the whole store is one encoding.
- **Ask the root, not the symptom.** The revised §89 (#1261) asks for uniform encoding (A or B), from which the O(1) `genome_append_kernel` falls out — instead of a narrow kernel-append that would leave the byte-TLV residue in place.

## Refinement — the ask is an API SURFACE, not a format choice (user, 2026-07-04)
The sharper framing: don't ask srmech "pick format A or B"; ask for **API access** where srmech handles the encoding differences gracefully at O(1) behind a first-class **kernel-store surface** (`kernel_store_pack`/`_append`/`_load`/`_labels`). The responsibility boundary is the point — the genome FORMAT is srmech's; siona should call a clean store API and never touch chunking / header / aligned-D. That siona HAD to hand-roll `add_kernel` (chunk→genome_append→back-compat trim) IS the `[[feedback_introspect_srmech_before_python_dispatch]]` "route-around" tell — the multi-kernel store is a srmech capability. siona's `genome_store` is a PROTOTYPE of that API, offered to upstream (#1261 comment); it becomes a thin shim once srmech ships the surface. Append is one method; graceful-O(1)-encoding is the store's contract (element_type recorded per-kernel so klein4/bits/float coexist, codec applied by srmech — F1043).

## Verdict / next
**The O(1) teach interim ships (`add_kernel`, aligned-D, honestly labeled), and the design question is answered: the root fix is a UNIFORM Klein-4 encoding — Klein-4-encode the §60 header (A) or move D to the manifest (B) — filed #1261. When it lands, `add_kernel` migrates to the uniform path and the mixed genome disappears; until then the interim is functionally exact (kernel_unpack transparently reads header'd + header-less).** Next: PKG-3 full-instrument pack once the uniform format lands (avoids baking the byte-TLV header into siona's shipped foundational kernel); the F1035 kernel pack can wait for it.
